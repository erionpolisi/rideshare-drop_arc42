== Deployment View

ifdef::arc42help[]
[role="arc42help"]
****
.Content
The deployment view describes:

 1. technical infrastructure used to execute your system, with infrastructure elements like geographical locations, environments, computers, processors, channels and net topologies as well as other infrastructure elements and

2. mapping of (software) building blocks to that infrastructure elements.

Often systems are executed in different environments, e.g. development environment, test environment, production environment. In such cases you should document all relevant environments.

Especially document a deployment view if your software is executed as distributed system with more than one computer, processor, server or container or when you design and construct your own hardware processors and chips.

From a software perspective it is sufficient to capture only those elements of an infrastructure that are needed to show a deployment of your building blocks. Hardware architects can go beyond that and describe an infrastructure to any level of detail they need to capture.

.Motivation
Software does not run without hardware.
This underlying infrastructure can and will influence a system and/or some
cross-cutting concepts. Therefore, there is a need to know the infrastructure.

.Form

Maybe a highest level deployment diagram is already contained in section 3.2. as
technical context with your own infrastructure as ONE black box. In this section one can
zoom into this black box using additional deployment diagrams:

* UML offers deployment diagrams to express that view. Use it, probably with nested diagrams,
when your infrastructure is more complex.
* When your (hardware) stakeholders prefer other kinds of diagrams rather than a deployment diagram, let them use any kind that is able to show nodes and channels of the infrastructure.


.Further Information

See https://docs.arc42.org/section-7/[Deployment View] in the arc42 documentation.

****
endif::arc42help[]

=== Infrastructure Level 1
image::../images/07_deployment_view.png["Deployment view Level 1"]
Motivation::
Drop is operated as a cloud-native application on Google Cloud
Platform (GCP). GCP was chosen because Firebase – which we use for
authentication, real-time database and push notifications – is native
to GCP, which keeps latency and operational overhead low.

The mobile apps run on the end users' devices; everything else runs in
GCP. Stripe and the Map & Routing Provider are reached over the public
Internet as managed third-party services.

Overview::

[cols="1,3", options="header"]
|===
| Node / Environment | Hosted Software

| End-user devices (Android, iOS)
| Flutter Client

| GCP – Cloud Run / GKE
| Backend Monolith (Spring Boot), Payment Service,
Tracking Service

| GCP – Cloud SQL (PostgreSQL)
| Operational data of the monolith (Identity, Rides, Matching,
Payments façade, Analytics Repository)

| GCP – Firebase
| Firebase Authentication, Firestore (real-time ride/location data),
Firebase Cloud Messaging (push)

| GCP – Pub/Sub or self-managed Kafka
| Internal domain event bus (e.g. `RideCompleted`,
`PaymentSettled`, `UserRegistered`)

| GCP – Cloud Logging / Cloud Monitoring / Grafana
| Logs, metrics, dashboards, alerting

| External – Stripe Connect
| Charges, driver payouts, commission split

| External – Map & Routing Provider
| Geocoding, routing, ETA

| External – Identity / Licence Verification (optional)
| Driver background checks
|===

Region and Network Topology::
* Primary GCP region: *`europe-west3` (Frankfurt)* with multi-zone
  deployment across `europe-west3-a`, `-b`, `-c` for zonal redundancy.
  Personal data therefore stays inside the EU (constraint OC1 / GDPR,
  ADR-5).
* One VPC per environment (`dev`, `staging`, `prod`) with two
  subnets: a *public* subnet for the HTTPS load balancer and Stripe
  webhook receiver, and a *private* subnet for all stateful services
  (Cloud SQL, internal Pub/Sub/Kafka, internal service-to-service
  calls over VPC-native networking).
* Egress to external providers (Stripe, Map & Routing, Verification)
  goes through Cloud NAT so outbound IPs are stable and can be
  allow-listed by the partner.
* Secrets (Stripe API keys, Firebase Admin credentials, JWT signing
  keys) are stored in GCP Secret Manager and mounted at startup.

Quality and/or Performance Features::
* *Scalability* – the Backend Monolith, the Payment Service and the
  Tracking Service are stateless and run behind a managed
  load balancer; they scale horizontally on CPU and request count.
* *Availability* – managed services (Firestore, Cloud SQL, Stripe)
  remove most of the operational burden from the small team.
* *Security* – TLS for every external channel, encryption at rest for
  Cloud SQL and Firestore, secrets in GCP Secret Manager, JWTs in
  HttpOnly/Secure cookies.
* *Cost* – pay-per-use services keep infrastructure cost low while the
  user base is still growing (constraint: tight budget, small team).

=== Infrastructure Level 2

==== Flutter Client

The Flutter app is distributed through the Apple App Store and the
Google Play Store. It bundles a thin Dart networking layer that talks
to the Backend Monolith over HTTPS, a Firebase SDK for authentication,
push and Firestore listeners, and native bridges for background GPS.

==== Backend Monolith

The Spring Boot monolith is packaged as a container image. A typical
production deployment runs at least two instances behind the load
balancer to survive a single-instance outage and autoscales up to
ten instances on CPU and request count. Each instance is stateless –
session state lives in the client JWT and in Firestore. The instances
share a Cloud SQL database (regional, multi-zone, with one read
replica) for persistent data and publish/consume events on the
internal event bus.

==== Payment Service

A dedicated service is used to keep PCI scope small. The service
exposes a narrow internal REST API to the monolith, calls Stripe
Connect over HTTPS, and receives Stripe webhooks on a dedicated
public endpoint that verifies the Stripe signature header.

==== Tracking Service

The Tracking Service is intentionally thin: most of the heavy lifting
is done by Firestore (real-time database) and FCM (push). The service
owns the schema and access rules of the ride / location documents and
fans out internal events when relevant state changes happen.

==== Environments

Three environments are operated with identical infrastructure
definitions:

[cols="1,3", options="header"]
|===
| Environment | Purpose

| `dev`     | Continuous deployment from `main` for the development team.
| `staging` | Pre-production verification, integration tests, UAT.
| `prod`    | End-user traffic.
|===

Infrastructure is provisioned as code (e.g. Terraform) so that the
three environments stay aligned.
