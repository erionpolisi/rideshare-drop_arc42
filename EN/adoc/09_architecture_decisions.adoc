The decisions below are the most consequential ones for *Drop*. They
are listed in lightweight ADR form: context, decision, consequences.
The summary already given in chapter 4 (Solution Strategy) points to
these decisions.

=== ADR-1: Cross-platform Mobile App with Flutter

Context::
The product must ship on both iOS and Android, but the regional company
has a relatively small team, a tight budget and must reach the market
quickly to compete with established providers.

Decision::
Build both apps from a single cross-platform code base in *Flutter /
Dart*, dropping to native code only where unavoidable (background GPS,
push notifications).

Consequences::
* (+) One code base, smaller team, faster delivery, consistent UX.
* (–) Framework dependency on Flutter; native bridges are still needed
  for maps and background location.
* (–) Some overhead for very heavy real-time map rendering.

=== ADR-2: Modular Monolith with Bounded Contexts and Gradual Microservice Extraction

Context::
Scalability for a large number of users and rides is a non-functional
requirement, yet the team is small and the principles *KISS* and
*YAGNI* warn against premature distribution. At the same time, two
bounded contexts have unusual non-functional requirements that already
justify their own deployment unit: Payments must keep PCI scope small
(ADR-3) and Tracking has very different scaling and connection-handling
characteristics (ADR-4).

Decision::
Start with a *modular monolith* with clear bounded contexts (Identity,
Rides, RideHistory, Notifications, Analytics) deployed as one unit.
Matching, Booking, Fare Estimation, Driver Assignment and Ride
Lifecycle live *inside* the Rides bounded context (see
<<section-building-block-view>>, Level 3). Keep the seams so that
high-load contexts can later be extracted into separate microservices.
The system is explicitly understood as a *transitional architecture*:
bounded contexts that already have technical reasons to be separate
are extracted *now* (Payments, Tracking); the others stay in the
monolith until measurable load, release-cadence or team-topology
pressure justifies their extraction.

Consequences::
* (+) Simple deployment and operations for the still-coupled contexts,
  fast development, easy debugging, low infrastructure cost.
* (+) Bounded contexts are ready for extraction once load justifies
  it; two are already extracted, proving the seams work.
* (+) Hybrid model lets the team learn microservice operations on a
  small surface (Payments, Tracking) before extracting more.
* (–) Requires discipline to keep boundaries clean inside the
  monolith.
* (–) Coarse-grained scaling for the contexts still inside the
  monolith; extraction work later when load grows.
* (–) Two operational models in parallel (monolith + microservices)
  increases the variety of deployment, monitoring and incident
  patterns the team must master.

=== ADR-3: Use Stripe Connect for Payments

Context::
The app must charge passengers, pay out drivers and take a commission,
while meeting the strict security and data-protection requirement and
PCI-DSS. The team has no in-house payment expertise.

Decision::
Use a PCI-DSS-compliant marketplace processor – *Stripe Connect* – for
charges, driver payouts and the commission split, instead of building
payment handling ourselves.

Consequences::
* (+) PCI scope offloaded; cards are tokenised (no card data stored).
* (+) Built-in split payouts and reporting.
* (–) Per-transaction fees reduce margin.
* (–) Vendor lock-in; dependency on Stripe availability – mitigated
  by the Circuit Breaker pattern (chapter 8).

=== ADR-4: Managed Real-time Messaging instead of Custom Sockets

Context::
Live driver location and ETA are core to the experience and must
stream to many concurrent rides with low latency. Building an own
socket layer is too costly for a small team.

Decision::
Stream driver location and ride status through a managed real-time
messaging service (Firebase Firestore listeners and Firebase Cloud
Messaging) instead of operating our own socket infrastructure.
Asynchronous communication between bounded contexts and extracted
microservices (including the Payment Service) is handled by domain
events on the internal Kafka event bus (ADR-6).

Consequences::
* (+) Low-latency updates, managed scaling and connection handling.
* (+) Built-in push and offline support.
* (–) Per-message / per-connection cost.
* (–) Vendor lock-in; update frequency must be tuned to balance
  battery life and data use.

=== ADR-5: Google Cloud Platform as Hosting Provider

Context::
Drop needs a cloud provider for the backend, the extracted
microservices, the operational database, monitoring and logging.
Firebase (Authentication, Firestore, FCM) was already selected as a
backing service in ADR-4. The team is small and wants to avoid the
operational overhead of running its own Kubernetes clusters across
multiple providers.

Decision::
Host the backend, the Payment Service, the Tracking Service, the
relational database (Cloud SQL / PostgreSQL) and the observability
stack on *Google Cloud Platform (GCP)*. Use *Cloud Run* for stateless
workloads and *GKE* only where Cloud Run's limits are reached.
Primary region is `europe-west` to keep personal data inside the EU
(constraint OC1 / GDPR).

Consequences::
* (+) Firebase is native to GCP – lower latency, single billing,
  single IAM model.
* (+) Cloud Run scales stateless services from zero in `dev` and
  `staging`, which keeps non-production cost low.
* (+) European region keeps GDPR data residency requirements
  straightforward.
* (–) Vendor lock-in to GCP for the operational stack.
* (–) JVM cold starts on Cloud Run are incompatible with the
  P95-latency SLO, so `prod` revisions run with `min-instances=2`
  and startup CPU boost (see chapter 7); this raises the prod cost
  baseline compared with pure scale-from-zero.
* (–) Some advanced networking features (e.g. multi-region
  active/active) require GKE rather than Cloud Run; revisit if needed
  (see technical debt D2).

=== ADR-6: Apache Kafka as Internal Event Bus

Context::
Bounded contexts inside the monolith and the extracted microservices
must exchange domain events (`RideCompleted`, `PaymentSettled`,
`UserRegistered`, …) asynchronously, without direct coupling. The bus
must survive consumer downtime (events kept until consumed) and allow
later replay for new consumers such as Analytics.

Decision::
Use *Apache Kafka* as the internal event bus, consumed as a managed
service on GCP (e.g. Confluent Cloud on GCP) so the team does not
operate brokers itself. The application code accesses the broker
through a thin `EventPublisher` / `EventSubscriber` interface so that
the concrete provider can be swapped later (e.g. for Google Cloud
Pub/Sub) without touching domain code.

Consequences::
* (+) Decouples bounded contexts and extracted microservices; events
  are durable and replayable.
* (+) Enables future consumers (Analytics, new microservices) to be
  added without touching producers.
* (+) Abstraction layer keeps the choice of broker reversible.
* (–) Managed Kafka has a per-message / throughput cost.
* (–) Event-schema evolution and idempotent consumers require extra
  discipline.
