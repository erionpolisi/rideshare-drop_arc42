== Building Block View

ifdef::arc42help[]
[role="arc42help"]
****
.Content
The building block view shows the static decomposition of the system into building blocks (modules, components, subsystems, classes, interfaces, packages, libraries, frameworks, layers, partitions, tiers, functions, macros, operations, data structures, ...) as well as their dependencies (relationships, associations, ...)

This view is mandatory for every architecture documentation.
In analogy to a house this is the _floor plan_.

.Motivation
Maintain an overview of your source code by making its structure understandable through
abstraction.

This allows you to communicate with your stakeholder on an abstract level without disclosing implementation details.

.Form
The building block view is a hierarchical collection of black boxes and white boxes
(see figure below) and their descriptions.

image::05_building_blocks-EN.png["Hierarchy of building blocks"]

*Level 1* is the white box description of the overall system together with black
box descriptions of all contained building blocks.

*Level 2* zooms into some building blocks of level 1.
Thus it contains the white box description of selected building blocks of level 1, together with black box descriptions of their internal building blocks.

*Level 3* zooms into selected building blocks of level 2, and so on.


.Further Information

See https://docs.arc42.org/section-5/[Building Block View] in the arc42 documentation.

****
endif::arc42help[]

=== Whitebox Overall System (Level 1)

image::images/05-level1-whitebox.png[Whitebox Drop (Level 1)]

*Rationale:* Drop is split by deployment unit — a Flutter *Mobile Client*
on the user's device and a Spring Boot *Backend* holding all business
logic. External capabilities the project does not build itself are
reached as neighbours (see <<section-context-and-scope>>).

*Contained building blocks:*

[cols="1,3", options="header"]
|===
| Building block | Description

| Mobile Client (Flutter)
| App for passengers and drivers; renders the UI, reads device GPS, and
talks to the Backend and Firebase (TC1).

| Backend (Spring Boot)
| Modular monolith that exposes a REST API and holds all business logic;
integrates Firebase, the Map & Routing provider and Stripe. Detailed at
Level 2.
|===

=== Backend — Whitebox (Level 2)

image::images/05-level2-backend.png[Backend Whitebox (Level 2)]

*Rationale:* The backend is a *modular monolith*: a functional
decomposition into modules whose boundaries match the services it may
later be split into. Modules communicate synchronously through the API
layer and asynchronously through a Kafka event bus, which keeps them
decoupled and eases the planned microservice extraction.

*Contained building blocks:*

[cols="1,3", options="header"]
|===
| Building block | Description

| API Layer
| REST facade; validates authentication and routes requests to the
modules.

| User & Identity
| Registration, profiles and driver verification; integrates Firebase
Authentication.

| Ride Management
| Ride search, matching, booking and ride lifecycle. Detailed at Level 3.

| Tracking
| Ingests driver locations, publishes them to the event bus, and exposes
live position to clients through Firestore.

| Payment
| Fare calculation, commission and driver payouts via Stripe.

| Notification
| Sends push notifications through Firebase Cloud Messaging.

| Ride History
| Stores and serves completed-ride records.

| Event Bus (Apache Kafka)
| Asynchronous event backbone decoupling the modules.
|===

=== Ride Management — Whitebox (Level 3)

image::images/05-level3-ride-management.png[Ride Management Whitebox (Level 3)]

*Rationale:* Ride Management follows the lifecycle of a ride, from the
booking request through driver matching and assignment to the tracked,
state-managed trip.

*Contained building blocks:*

[cols="1,3", options="header"]
|===
| Building block | Description

| Booking
| Creates and manages booking requests; orchestrates the other blocks.

| Fare Estimation
| Calls the Map & Routing provider for distance and ETA and computes the
fare.

| Ride Search & Matching
| Finds nearby available drivers for a request.

| Driver Assignment
| Offers rides to drivers and handles accept / decline.

| Ride Lifecycle
| State machine for a ride (requested → accepted → in progress →
completed / cancelled); emits ride events and persists state.
|===
