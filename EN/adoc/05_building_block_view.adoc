== Building Block View

ifdef::arc42help[]
[role="arc42help"]
****
.Content
The building block view shows the static decomposition of the system into building blocks (modules, components, subsystems, classes, interfaces, packages, libraries, frameworks, layers, partitions, tiers, functions, macros, operations, data structures, ...) as well as their dependencies (relationships, associations, ...)

This view is mandatory for every architecture documentation.
In analogy to a house this is the _floor plan_.

.Motivation
Maintain an overview of your source code by making its structure understandable through
abstraction.

This allows you to communicate with your stakeholder on an abstract level without disclosing implementation details.

.Form
The building block view is a hierarchical collection of black boxes and white boxes
(see figure below) and their descriptions.

image::05_building_blocks-EN.png["Hierarchy of building blocks"]

*Level 1* is the white box description of the overall system together with black
box descriptions of all contained building blocks.

*Level 2* zooms into some building blocks of level 1.
Thus it contains the white box description of selected building blocks of level 1, together with black box descriptions of their internal building blocks.

*Level 3* zooms into selected building blocks of level 2, and so on.


.Further Information

See https://docs.arc42.org/section-5/[Building Block View] in the arc42 documentation.

****
endif::arc42help[]

=== Whitebox Overall System

image::05_level1.png["Level 1 - Overall system: Mobile App, Backend (modular monolith), Payment Service, Realtime Service, Analytics Repository and external systems"]

Motivation::
Drop is decomposed into a small number of coarse-grained building
blocks. The split reflects the solution strategy (chapter 4): a single
mobile codebase, a modular Spring Boot backend with clear bounded
contexts, and a small number of selected microservices for capabilities
that need independent scaling (payments, real-time location). External
systems are kept as black boxes.

Contained Building Blocks::

[cols="1,3", options="header"]
|===
| Name | Responsibility

| Mobile App
| Flutter-based client for Android and iOS. Renders the UI for
passengers and drivers, calls the backend over HTTPS, and subscribes to
real-time updates.

| Backend
| Spring Boot modular monolith. Holds the core business logic and
exposes the REST API for all use cases (registration, search, booking,
ride lifecycle, history, reporting).

| Payment Service
| Microservice that integrates with Stripe Connect for charges, driver
payouts and commission split. Isolates PCI scope from the monolith.

| Realtime / Location Service
| Microservice that streams driver location and ride status updates to
clients via a managed pub/sub channel (Firestore / FCM).

| Analytics Repository
| Stores and aggregates operational, revenue and user metrics for
reporting and business intelligence.

| External Systems
| Map & Routing Provider, Identity / Licence Verification, Stripe and
Push Notification Service. Described as external actors in chapter 3.
|===

Important Interfaces::

* *Mobile App <-> Backend* – REST/HTTPS API for business operations;
  JWT in an HttpOnly, Secure cookie (issued by the external identity
  provider).
* *Mobile App <-> Realtime Service* – Firestore listeners (WebSocket)
  and Firebase Cloud Messaging for push.
* *Backend <-> Payment Service* – Internal REST plus Stripe webhooks for
  asynchronous settlement events.
* *Backend <-> External Map / Identity providers* – HTTPS, guarded by
  Circuit Breaker and Retry-with-Backoff (see chapter 8).

=== Level 2

This level zooms into the *Backend* monolith, which contains the bulk
of the business logic. The monolith is structured as a set of bounded
contexts. The boundaries are enforced in code (package boundaries, no
direct cross-context calls) so that high-load contexts can later be
extracted as microservices without rewriting them.

==== White Box: Backend (Modular Monolith)

image::05_level2_backend.png["Level 2 - Backend modular monolith with bounded contexts: Identity, Matching, Rides, Payments, Analytics, Notifications"]

Motivation::
Splitting the backend into bounded contexts gives the small team the
simplicity of a single deployable unit while preserving clear seams for
future extraction. Each context owns its data and exposes a controller
layer for the REST API and an internal interface for the other
contexts.

Contained Building Blocks::

[cols="1,3", options="header"]
|===
| Context | Responsibility

| Identity
| User registration, profile management, role assignment
(Passenger / Driver / Admin), session/JWT handling.

| Matching
| Search for nearby rides, driver assignment, dispatch of ride
requests to drivers.

| Rides
| Ride lifecycle: booking, acceptance/decline, tracking handover to
the Realtime Service, completion, history.

| Payments
| Façade in front of the Payment Service. Translates ride completion
into a charge + payout + commission split through Stripe Connect.

| Analytics
| Collects domain events from the other contexts (ride completed,
payment processed, user registered) and feeds them into the
*Analytics Repository* (see Level 3).

| Notifications
| Sends transactional notifications (ride status, payouts) through the
external Push Notification Service.
|===

Important Interfaces::

* Each context exposes a REST controller package.
* Cross-context communication uses domain events published on Kafka
  (e.g. `RideCompleted`, `PaymentSettled`, `UserRegistered`) instead
  of direct method calls. This keeps contexts decoupled and prepares
  them for extraction.

=== Level 3

This level zooms into the *Analytics* context from Level 2, because it
has the most architecturally relevant internal structure: it is the
only context organised around a dedicated repository with several
domain-specific aggregates.

==== White Box: Analytics Repository

image::05_level3_analytics.png["Level 3 - Analytics Repository with ReportsController, AnalyticsController, RideAnalytics, RevenueAnalytics, UserAnalytics and AnalyticsRecord"]

Purpose::
The Analytics Repository is responsible for collecting, storing and
providing analytical data related to ride activity, revenue generation
and user engagement.

Responsibilities::
* Aggregate operational data
* Store analytical metrics
* Provide reports to controllers
* Support business intelligence functions
* Enable revenue and usage analysis

Contained Building Blocks::

[cols="1,3", options="header"]
|===
| Name | Responsibility

| AnalyticsRepository
| Central repository that manages analytics data and provides access to
the different analytical domains. Used by `ReportsController` and
`AnalyticsController`. Persists analytics information, retrieves
analytical metrics, aggregates data from analytical records and
provides reporting data.

| ReportsController
| Generates and serves business reports. Requests analytics data from
`AnalyticsRepository`, generates reports and exposes report endpoints.

| AnalyticsController
| Exposes analytics-related APIs. Serves analytics requests, retrieves
metrics from `AnalyticsRepository` and delivers analytical summaries.

| RideAnalytics
| Operational metrics. Attributes: `totalRides : int`,
`averageDistance : double`, `averageDuration : double`. Tracks ride
volume and calculates average trip distance and duration.

| RevenueAnalytics
| Financial performance metrics. Attributes:
`totalRevenue : double`, `averageFare : double`. Tracks platform
revenue, calculates average fare values and supports financial
reporting.

| UserAnalytics
| User activity metrics. Attributes: `activeUsers : int`,
`completedRides : int`. Monitors active user base, measures user
engagement and tracks ride completion statistics.

| AnalyticsRecord
| Generic analytical data record representing an individual metric.
Attributes: `metricName : String`, `metricValue : double`. Stores
metric values, supports aggregation and provides historical analytical
data.
|===

Relationships::

[cols="2,1,2", options="header"]
|===
| Source | Relationship | Target

| AnalyticsRepository | Aggregates | RideAnalytics
| AnalyticsRepository | Aggregates | RevenueAnalytics
| AnalyticsRepository | Aggregates | UserAnalytics
| RideAnalytics       | Contains   | AnalyticsRecord (1..*)
| RevenueAnalytics    | Contains   | AnalyticsRecord (1..*)
| UserAnalytics       | Contains   | AnalyticsRecord (1..*)
| ReportsController   | Uses       | AnalyticsRepository
| AnalyticsController | Uses       | AnalyticsRepository
|===

Architectural Rationale::

The Analytics subsystem follows a repository-centred design:

. Controllers remain independent from analytics storage details.
. `AnalyticsRepository` acts as a single access point for analytical
  data.
. Domain-specific analytics objects (`RideAnalytics`,
  `RevenueAnalytics`, `UserAnalytics`) separate concerns.
. `AnalyticsRecord` provides a reusable structure for storing metrics.
. The design supports future extension with additional analytics
  domains without modifying existing controllers.

Quality Goals Supported::
* *Maintainability* – clear separation between controllers and data
  storage.
* *Scalability* – new analytics categories can be added easily.
* *Reusability* – the common `AnalyticsRecord` structure is reused
  across all analytical domains.
* *Modifiability* – analytics calculations can evolve independently
  from the API layer.
