== Building Block View

ifdef::arc42help[]
[role="arc42help"]
****
.Content
The building block view shows the static decomposition of the system into building blocks (modules, components, subsystems, classes, interfaces, packages, libraries, frameworks, layers, partitions, tiers, functions, macros, operations, data structures, ...) as well as their dependencies (relationships, associations, ...)

This view is mandatory for every architecture documentation.
In analogy to a house this is the _floor plan_.

.Motivation
Maintain an overview of your source code by making its structure understandable through
abstraction.

This allows you to communicate with your stakeholder on an abstract level without disclosing implementation details.

.Form
The building block view is a hierarchical collection of black boxes and white boxes
(see figure below) and their descriptions.

image::05_building_blocks-EN.png["Hierarchy of building blocks"]

*Level 1* is the white box description of the overall system together with black
box descriptions of all contained building blocks.

*Level 2* zooms into some building blocks of level 1.
Thus it contains the white box description of selected building blocks of level 1, together with black box descriptions of their internal building blocks.

*Level 3* zooms into selected building blocks of level 2, and so on.


.Further Information

See https://docs.arc42.org/section-5/[Building Block View] in the arc42 documentation.

****
endif::arc42help[]

=== Whitebox Overall System (Level 1)

image::05_level1.png[Whitebox Drop (Level 1)]

*Rationale:* Drop is split by deployment unit. The mobile *Flutter
Client* runs on the user's device. The server side started as one
deployable monolith and is being incrementally split into microservices
as load and team size grow (ADR-2). At the moment three server-side
deployment units exist: the *Backend Monolith* (Spring Boot) holding
the still-coupled bounded contexts, and the already-extracted
*Payment Service* (ADR-3) and *Tracking Service* (ADR-4). The three
server-side units are integrated asynchronously through a shared
*Event Bus* (Apache Kafka, ADR-6). External neighbouring systems
(Firebase, Stripe Connect, Map & Routing Provider, Identity & Licence
Verification) are described in <<section-context-and-scope>>.

*Contained building blocks:*

[cols="1,3", options="header"]
|===
| Building block | Description

| Flutter Client
| App for passengers and drivers; renders the UI, reads device GPS, and
talks to the Backend Monolith and Firebase (TC1).

| Backend Monolith
| Spring Boot modular monolith that exposes the REST API and holds the
business logic of Identity, Rides, Notifications, RideHistory and
Analytics. Publishes and consumes domain events on the *Event Bus*.
Detailed at Level 2.

| Payment Service
| Microservice already extracted from the monolith. Integrates Stripe
Connect for charges, payouts and the commission split (ADR-3) and
publishes `PaymentSettled` / `PaymentFailed` events on the *Event
Bus*.

| Tracking Service
| Microservice already extracted from the monolith. Owns the
high-frequency driver-location data and streams driver positions and
ride-status updates to the *Flutter Client* through *Firestore*
(ADR-4). Encapsulates the *Map & Routing Provider* (ETA, routing).
Publishes location-related events on the *Event Bus*.

| Event Bus (Apache Kafka)
| Asynchronous integration backbone shared by the *Backend Monolith*,
*Payment Service* and *Tracking Service*; carries the cross-context
domain events (`RideRequested`, `RideAccepted`, `RideCompleted`,
`PaymentSettled`, `PaymentFailed`, ...). See ADR-6.
|===

=== Backend Monolith — Whitebox (Level 2)

image::05_level2_backend.png[Backend Monolith Whitebox (Level 2)]

*Rationale:* The Backend Monolith is a *modular monolith*: a
functional decomposition into bounded-context modules whose boundaries
match the services it may later be split into (ADR-2). Modules
communicate synchronously through the API Layer and asynchronously by
publishing and consuming events on the *Event Bus* (see Level 1),
which keeps them decoupled and eases the planned microservice
extraction. Payments and Tracking have already been extracted (see
Level 1); the remaining modules are described below.

*Contained building blocks:*

[cols="1,3", options="header"]
|===
| Building block | Description

| API Layer
| REST facade; validates authentication and routes requests to the
modules.

| Identity
| Registration, profiles and driver verification; integrates Firebase
Authentication.

| Rides
| Ride booking, fare estimation, matching, driver assignment and
ride lifecycle. Detailed at Level 3.

| Notifications
| Sends push notifications through *Firebase Cloud Messaging* (FCM).
Exposes an internal REST endpoint that *Rides* calls (fire-and-forget,
behind a Circuit Breaker, see <<section-concepts>>) to trigger
user-facing pushes such as booking confirmation, driver offer and
receipt. Additionally subscribes to `PaymentSettled` and
`PaymentFailed` on the *Event Bus* so that payment-outcome
notifications originating outside *Rides* are delivered
asynchronously.

| RideHistory
| Stores and serves completed-ride records; consumes `RideCompleted`
from the Event Bus.

| Analytics
| Consumes domain events (`RideCompleted`, `PaymentSettled`,
`PaymentFailed`, `UserRegistered`) from the Event Bus and aggregates
business KPIs.
|===

=== Level 3

==== Rides — Whitebox (Level 3)

image::05_level3_rides.png[Rides Whitebox (Level 3)]

*Rationale:* Rides is decomposed by responsibility along the
ride-booking flow: receiving the request (Booking), pricing it
(Fare Estimation), finding candidate drivers (Matching), offering
the ride to a driver (Driver Assignment) and persisting the
ride state during its lifetime (Ride Lifecycle). Booking is the
orchestrator; the others are called in sequence or in response to
driver actions. All location- and routing-related calls go through
the *Tracking Service* (see <<section-building-block-view>>, Level 1) -
Rides never talks to the *Map & Routing Provider* directly. Ride
Lifecycle is the *only* emitter of domain events from Rides and
owns the `Ride` entity; the events are consumed asynchronously by
*Notifications*, *Analytics* and *RideHistory* via the Event Bus.
The only synchronous outbound dependency of Rides is the call from
Ride Lifecycle to the extracted *Payment Service* when a ride
transitions to `COMPLETED`, because the charge confirmation is
needed before the response is returned to the client.

*Contained building blocks (blackboxes):*

[cols="1,3", options="header"]
|===
| Building block | Description

| Booking
| Application-service blackbox. Receives the REST request from the
API Layer, orchestrates the other blackboxes and returns the booking
confirmation. Idempotent on the client-supplied idempotency key
(see <<section-concepts>>).

| Fare Estimation
| Computes the fare from distance and ETA. Distance and ETA are
obtained from the *Tracking Service* (see <<section-building-block-view>>,
Level 1), which encapsulates the call to the *Map & Routing
Provider*. Stateless.

| Matching
| Finds nearby available drivers for a booking request. Reads
driver availability through the *Tracking Service*; ranks the
candidates by ETA and proximity.

| Driver Assignment
| Coordinator for the offer loop: takes the ranked candidate list
from *Matching*, picks the next driver to offer, hands the offer to
*Ride Lifecycle* (which then publishes `RideRequested` on the
Event Bus, see below), waits for the driver's response within a
configurable timeout and advances to the next candidate on decline
or timeout. *Driver Assignment never pushes to the driver itself* -
the push is delivered asynchronously by *Notifications* (FCM); the
driver's reply arrives synchronously via the *API Layer* and is
routed back here.

| Ride Lifecycle
| Owns the `Ride` aggregate, persists it and implements its state
machine (`REQUESTED` → `ACCEPTED` → `IN_PROGRESS` → `COMPLETED` /
`CANCELLED`). Publishes `RideRequested`, `RideAccepted`,
`RideCompleted` and `RideCancelled` on the Event Bus. On the
`COMPLETED` transition it additionally calls the extracted
*Payment Service* synchronously (REST) to charge the passenger,
because the response to the client must contain the payment outcome.
|===
