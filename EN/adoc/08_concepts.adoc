This chapter collects the concepts that span multiple building blocks
of *Drop* and that must therefore be applied consistently across the
whole system.

=== Layering, Pub/Sub and Resilience Patterns

Drop combines a modular monolith with a small number of selected
microservices. Inside every component the same layering is used –
controller, application service, domain, infrastructure – so that the
same patterns apply everywhere.

Core domains (Identity, Matching, Rides, Payments) are structured as
*bounded contexts*. They do not call each other directly: cross-context
communication uses *publish/subscribe* over the internal event bus
(domain events such as `RideCompleted`, `PaymentSettled`,
`UserRegistered`). Scalable real-time features (driver location, ride
status to the apps) use a managed pub/sub channel (Firestore / FCM).

To stay resilient against flaky networks and external dependencies the
following patterns are applied at every outbound call:

* *Circuit Breaker* – open the circuit after a configurable failure
  rate; fail fast instead of stacking up requests.
* *Retry with Exponential Backoff* – for idempotent operations only.
* *Idempotency Keys* – on every write endpoint that can be retried by
  the client (e.g. booking, payment).
* *RFC 7807 Problem Details* – standardised error responses across all
  REST APIs so that the apps can render uniform error messages.

=== Security and Authorisation

Authentication is required at every entry point; authorisation is
checked on every sensitive action.

* *Identity* – delegated to Firebase Authentication; Drop never stores
  passwords.
* *Tokens* – Firebase ID tokens (JWT, RFC 7519) issued by Firebase
  Authentication. The mobile apps store the token in the platform's
  secure storage (iOS Keychain / Android Keystore) and send it to the
  backend as an `Authorization: Bearer` header. Tokens carry the user
  ID and the role; refresh is handled by the Firebase SDK.
* *Roles* – `PASSENGER`, `DRIVER`, `ADMIN`. Role checks are enforced in
  the backend, not in the app.
* *Service-to-service* – calls between the Backend Monolith, the
  Payment Service and the Tracking Service are authenticated with
  Google-signed IAM ID tokens; Cloud Run ingress is restricted to
  internal traffic and the load balancer.
* *API edge* – the global HTTPS load balancer is fronted by Cloud Armor
  for WAF rules, IP allow-listing of Stripe webhooks and per-endpoint
  rate limiting to protect against abuse and DDoS.
* *Transport* – TLS on every external channel (mobile ↔ backend,
  backend ↔ external services, webhooks).
* *At rest* – encryption for Cloud SQL and Firestore; secrets in GCP
  Secret Manager.
* *Payment data* – card data is *never* stored in Drop; only Stripe
  payment-processor tokens are persisted (constraint OC1, ADR-3).
  Incoming Stripe webhooks are verified by signature and deduplicated
  by Stripe `event.id` to make webhook processing idempotent.

=== Mobile App Security

The Flutter client enforces the following controls in addition to the
backend rules above:

* *Secure token storage* – Firebase ID and refresh tokens are stored
  in the platform secure storage (iOS Keychain, Android Keystore);
  never written to logs or shared preferences.
* *TLS certificate pinning* – the public-key pin of the backend
  certificate is shipped with the app to prevent MITM via a rogue CA.
* *App attestation* – Play Integrity (Android) and App Attest (iOS)
  tokens are sent on sensitive calls (registration, payment) so the
  backend can reject requests from tampered or emulated clients.
* *Jailbreak / root detection* – the app refuses to start sensitive
  flows on a rooted or jailbroken device.
* *Deep links* – only an explicit allow-list of `https://` universal
  links is honoured; custom-scheme deep links are ignored.
* *Logging hygiene* – no PII, tokens or location data are written to
  device logs or crash reports.

=== Observability and Incident Response

Drop is operated against the SLOs defined in chapter 10. Observability
and on-call are designed so that an SLO breach is detected and routed
to a human before it becomes user-visible at scale.

* *Telemetry* – application logs to Cloud Logging (structured JSON,
  request-id correlated), metrics to Cloud Monitoring, distributed
  traces via OpenTelemetry to Cloud Trace across the Backend Monolith,
  Payment Service and Tracking Service.
* *SLI / SLO alerts* – burn-rate alerts in Cloud Monitoring for each
  SLO in chapter 10 (availability, P95 booking latency, tracking
  freshness). Multi-window (1 h / 6 h) burn-rate policy.
* *Paging* – alerts fire into PagerDuty with a SEV-1 / SEV-2 / SEV-3
  classification; SEV-1 (user-facing outage, payment outage, data
  breach) pages the on-call engineer 24/7, SEV-2 within business
  hours, SEV-3 creates a ticket.
* *Runbooks* – every alert references a runbook in the repository
  (`/docs/runbooks/<alert-id>.md`) covering triage, mitigation and
  escalation steps.
* *Postmortems* – every SEV-1 and SEV-2 incident produces a blameless
  postmortem within five working days, tracked in the same repository.

=== Testing

The system follows a *Test-Driven Development* (TDD) approach. Tests
are layered:

* *Unit tests* – per class / domain rule, fast feedback in CI.
* *Integration tests* – per bounded context, against a real database
  and an in-memory event bus.
* *Contract tests* – for the REST API and for the Stripe webhook
  endpoint.
* *End-to-end tests* – cover the critical user journeys (registration,
  booking, completion, payment).
* *Security and performance tests* – run on a schedule against the
  `staging` environment.

=== CI/CD

Every commit triggers the CI/CD pipeline:

. Static analysis and unit tests on every push.
. Build of container images and the Flutter app bundles.
. Integration and contract tests on `dev`.
. Manual approval gate, then promotion to `staging` and `prod`.
. Mobile builds are uploaded to the App Store and Play Store
  test tracks.

Infrastructure is provisioned as code so that `dev`, `staging` and
`prod` stay in sync.

=== Persistence

Drop uses a *polyglot persistence* approach: each data class is stored
where its access pattern fits best, but the choice is made centrally
so that the pattern is consistent across all bounded contexts.

* *Cloud SQL (PostgreSQL)* – relational store for transactional,
  consistency-critical data: identities, ride records, payment
  ledger, `AnalyticsRecord` entries. One regional Cloud SQL instance
  per environment (multi-zone, with one read replica in `prod`).
* *Firestore* – real-time, document store for live data that the
  apps must observe through listeners: current driver locations,
  live ride status. Strong eventual-consistency is acceptable here.
* *In-memory caches* – per-instance only; nothing that must survive a
  restart goes into a cache.

Cross-cutting rules:

* *Ownership* – every table / collection has exactly one owning
  bounded context. Other contexts read only through the owner's API
  or through domain events; no direct cross-context SQL joins.
* *Schema migrations* – versioned, forward-only migrations run on
  application startup (Flyway). Every migration must be additive and
  backwards-compatible during one release cycle so that rolling
  deploys never break a running instance.
* *Backups* – Cloud SQL automated daily snapshots with 30-day
  retention; Firestore export to Cloud Storage on a daily schedule.
  Restore is exercised at least once per release cycle.
* *Encryption at rest* – enabled on Cloud SQL and Firestore;
  application-level encryption for free-text fields that may contain
  personal data (constraint OC1 / GDPR).
* *Data retention* – ride and payment records are retained for the
  legally required period; live location data in Firestore is
  deleted at most 24 hours after the ride completes.
